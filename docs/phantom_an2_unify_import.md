# Importing the Phantom `.an2` files into Unify 5.2 — required changes

Status, 2026-09-28: the NIST export page's **Unify 5.2** target does the blocking changes, with the ICD values
as settings that still hold placeholders; see [`nist-export-plan.md`](nist-export-plan.md) §7 and the checklist
in §7 below.

Analysis of the synthetic enrolment files produced by Phantom against the Unify
ABIS API, version 5.2 (`prum_docs/biometrics/abis/api_5.2/api_v1.yaml`).

**Verdict:** both files are structurally valid ANSI/NIST-ITL traditional-encoding
transactions (every record parses, all `LEN` values are consistent, `1.003 CNT`
matches the records present). They **cannot be imported as-is**: every image
uses a compression Unify does not accept, three records use finger/palm
positions Unify does not accept, and the transaction type is almost certainly
not a configured TOT. Several further fields must be aligned with the project
ICD, which is not part of the `api_5.2` folder.

> The subject data is synthetic ("This person does not exist … Don't use it as
> evidence of matching accuracy or enrol it in live systems"). Any import must
> go to a test Unify instance only.

## 2. How the file would be submitted

`api_v1.yaml` offers three NIST upload endpoints. All take the file as the
multipart field `nistFile`, described only as *"A nist file according to ICD
defined"*:

| Endpoint | Use | Notes |
|---|---|---|
| `POST /transactions/enroll/nist` | Enrol | Optional `enrollNistParameters` (JSON part): `transactionId`, `printThresholdProfileName`, `portraitThresholdProfileName`. |
| `POST /transactions/nist` | Enrol, query or external search reply | Case type comes from the TOT. Needs a default threshold profile (enrol) or default register search (query) configured for the calling system. |
| `POST /transactions/compare/nist` | 1:1 compare | Not relevant for enrolment. |

`/transactions/enroll/nist` is the natural choice for these files. The call is
asynchronous: a `200` only means the file was received. Workflow validation
happens afterwards and a rejection arrives as a `stateChangeCallback`. A file
that passes the HTTP call can therefore still be rejected for any of the
problems below.

## 3. Blocking changes (spec says these will not be accepted)

### 3.1 Re-encode every image

The API spec restricts image compression per modality:

| Modality | Allowed by Unify (`imageFormat`) | Allowed bit depth | In file |
|---|---|---|---|
| Print / palm | `1` WSQ 2.0, `4` JPEG 2000 | 8 | PNG |
| Portrait | `2` JPEG, `4` JPEG 2000 | 8, 24, 32 | PNG |

PNG is a legal ANSI/NIST CGA code, but Unify does not accept it. All 20 image
records must be re-encoded.

**Type-14 and Type-15 (17 records)**

- Encode the grey image as **WSQ 2.0** (the norm for 500 ppi friction ridge)
  and set `14.011` / `15.011` to `WSQ20`.
  - Alternative: JPEG 2000, CGA `JP2` (lossy) or `JP2L` (lossless). JPEG 2000
    is mainly intended for 1000 ppi. Use it only if the ICD asks for it.
- Keep `.006 HLL`, `.007 VLL`, `.008 SLC`, `.009 THPS`, `.010 TVPS` and `.012 BPX = 8`
  unchanged. WSQ does not change the image dimensions.
- WSQ encoders: NBIS `cwsq`, or the WSQ support already in this repo
  (`lib/abis_next/fingerprint/formats/wsq.ex`). Use the standard 0.75 bit rate
  (≈15:1) unless the ICD says otherwise.

**Type-10 (3 records)**

- Encode as baseline **JPEG** and set `10.011` to `JPEGB`, or as JPEG 2000
  (`JP2` / `JP2L`).
- Keep `10.012 CSP = SRGB`, which fits a 24-bit colour JPEG.
- Strip the PNG alpha channel if there is one. JPEG has none, and Unify
  allows 32 bits only through JPEG 2000.

**Every re-encoded record**

- Replace the `.999 DATA` payload with the new bytes.
- Recompute the record's `.001 LEN`. The Type-1 record's own length is not
  affected, but every re-encoded record's is.
- The total file size will drop from ~33 MB to a few MB, mostly because the
  two 2750 × 4000 full-palm PNGs (~9 MB each) shrink.

### 3.2 Remove or remap unsupported positions

Unify accepts these print positions: `1–10`, `11`, `12` (control thumbs),
`13`, `14` (slaps), `22`, `24` (writer's palms), and `25–28` (lower/upper
palms). Three records fall outside this list.

| Record | Current | Problem | Options |
|---|---|---|---|
| IDC 16, Type-14 | FGP `15` (two thumbs) | Not in Unify's list | **(a)** Drop the record. **(b)** Split it into two single-thumb flat records, FGP `11` (right control thumb) and FGP `12` (left control thumb), `14.003 IMP = 0`. The ground truth (`fgp15_Two_thumbs.json`) places the left thumb (fgp 6) core at x≈441 and the right thumb (fgp 1) core at x≈1195 in the 1600 px image, so a split near the vertical midline is safe. |
| IDC 17, Type-15 | PLP `21` (right full palm) | Not in Unify's list | **(a)** Drop the record and keep only the writer's palm (22). **(b)** Split the full palm into **right upper palm (26)** and **right lower palm (25)**. The upper crop covers the interdigital area and triradii `a`–`d` below the fingers. The lower crop covers the thenar and hypothenar area and triradius `t`. Let the crops overlap a little, as ANSI/NIST recommends. The triradii coordinates in `plp21_R_full_palm.json` show where to cut. |
| IDC 19, Type-15 | PLP `23` (left full palm) | Not in Unify's list | Same as above: drop, or split into **left upper (28)** and **left lower (27)**. |

After removing or adding records:

- Renumber the IDCs if needed and **rewrite `1.003 CNT`**. Its first subfield
  (`1<US>21`) is the number of records after Type-1, and the IDC list must
  match the records actually present.
- If crops are made, set `.006 HLL` / `.007 VLL` to the crop size. Any
  downstream use of the ground truth JSON must shift coordinates by the
  crop offset.

### 3.3 Transaction type (`1.004 TOT`)

- `ENROL` is not a TOT documented anywhere in the Unify or PCSC material. The
  README says valid TOTs are project-specific, and the documented TOTs
  (`CPS`, `PMS`, `MPS`, `MMS`, `DBS`, `SRE`, `ERR`) are all three-letter codes.
- The TOT selects the case type and workflow. The calling system must be
  configured in Unify to use that case type, or the transaction is rejected.
- **Change:** set `1.004` to the enrolment TOT defined in the ICD for the test
  calling system, for example a criminal tenprint enrolment TOT. Update
  `2.005`, which currently repeats `ENROL`, the same way if that field is kept.

## 4. Probably required changes (depend on the ICD)

The API spec defers NIST content to *"project specific documents"*. The ICD is
not in `api_5.2/`, so these cannot be confirmed. They are nevertheless very
likely to need changing.

### 4.1 Type-1 header

| Field | Current | Likely required |
|---|---|---|
| `1.002 VER` | `0502` | Valid for ANSI/NIST-ITL 1-2011 Update 2015. Keep it unless the ICD names another profile. Note: if `1.013 DOM` is set to a profile such as INT-I, `VER` must match *that* profile's edition. INT-I 4.22 uses `0300` (see `integrations/pcsc/nist-versjonsnummer-int-i.md`). |
| `1.007 DAI` | `PHANTOM` | ORI of the receiving Unify system as defined in the ICD. |
| `1.008 ORI` | `PHANTOM` | ORI of the submitting (calling) agency. It probably has to match the calling-system configuration in Unify. |
| `1.009 TCN` | `PH-6693-6710-ENROL-20260925124526` | Must follow the ICD's TCN format. Some profiles require a fixed format with a check character (INT-I uses a modulo-23 check letter). Also must be unique per submission, so change it on every resend. |
| `1.013 DOM` | `PHANTOM <US> 1` | The domain name and version the ICD specifies, such as `NORAM` or a national or INT-I profile. `PHANTOM` is not a recognised domain. |
| `1.011 NSR`, `1.012 NTR` | `00.00` | Correct as long as the file has no Type-4 records. Keep them. |
| `1.006 PRY`, `1.014 GMT`, `1.015 DCS` | missing | Optional in the standard. Add them if the ICD makes them mandatory. |

### 4.2 Type-2 record

The Type-2 record currently holds only generator metadata in fields
`2.003`–`2.008`. The meaning of Type-2 fields is defined entirely by the ICD,
and an enrolment workflow normally validates person data from it (Unify
exposes this as TOT-specific `metadata`). Expect to:

- **Replace** fields `2.003`–`2.008` with the fields the ICD defines for the
  enrolment TOT. Typically these are name, date of birth, sex, nationality,
  case or reference number and claimed identity or register. The synthetic
  attributes in `subject.json` (sex `male`, age 21, and so on) can fill in
  plausible values.
- **Keep the provenance somewhere.** The Phantom run, subject and seed are
  useful for tracing a test enrolment back to its generator. Put them in an
  ICD-allowed free-text or reference field, or record them outside the file
  keyed by TCN or `transactionId`. Do not keep them in field numbers that the
  ICD assigns a different meaning to.
- Keep `2.002 IDC = 0`.

### 4.3 Source agency in image records

`10.004`, `14.004` and `15.004` (SRC) are `PHANTOM`. Set them to the same ORI
as `1.008`, or to whatever the ICD requires.

### 4.4 Fields `14.901` and `15.901`

Every Type-14 and Type-15 record carries a field `.901` with the value `2`.
Neither the Unify API docs nor the rest of the file explain what it means. A
strict validator may reject an unknown field. **Remove it**, unless the ICD
defines it.

## 5. Recommended consistency fixes

These are unlikely to block a test import, but Unify maps them onto sample
attributes. Wrong values give misleading test data.

| Field | Current | Issue | Suggested change |
|---|---|---|---|
| `14.003 IMP`, fingers | `1` (rolled live-scan) / `0` (plain live-scan) | Maps to Unify `captureType = Optical` | Fine. Keep it if the prints should be treated as live-scan. |
| `15.003 IMP`, palms | `11` (nonlive-scan palm) | Maps to `captureType = Inked`, which contradicts the fingers being live-scan | Use `10` (live-scan palm) so that all prints share one capture type. The alternative is to switch the fingers to `3` (rolled nonlive-scan) and `2` (plain nonlive-scan). |
| `10.013 SAP` | `20` | In ANSI/NIST-ITL, `20` is the *PIV* facial profile, which does not describe a police booking photo | Use `30` (legacy mugshot) or `32` (best practice level 30), or whatever the ICD specifies. |
| Slaps FGP 13, 14 (and any thumb split) | no segmentation | Without segment positions, Unify has to segment the slaps itself | Add `14.021 SEG` segment boxes if the ICD wants them. Finger cores in `fgp13_Right_four.json` and `fgp14_Left_four.json` give a starting point. |
| `10.026 SXS` | missing | Optional | Add `BEARD` for this subject (short full beard). This maps to Unify's portrait `descriptionCodes`. |

## 6. What already conforms

- Traditional (binary/tagged) encoding, well-formed. All `LEN` values and the
  `1.003 CNT` contents are consistent.
- Print resolution is 500 ppi, one of Unify's two allowed values (500 and 1000).
- Print bit depth is 8, the only value Unify allows.
- Finger positions 1–10, 13 and 14, and palm positions 22 and 24, are valid.
- Face poses `F`, `L` and `R` are valid values of `10.020`.
- Type-10 sets `10.005 PHD`, which maps to Unify's required portrait
  `captureDate`.
- `1.002 VER = 0502` is a legal version for ANSI/NIST-ITL 1-2011 Update 2015.
